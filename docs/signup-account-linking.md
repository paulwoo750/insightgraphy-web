# 가입 계정의 기존 학회원 연결: 자동 연결 → 관리자 연결

STEP 20(다섯 기록 테이블)·STEP 21(나머지 학회원 데이터)은 "승인 학회원 = `members.status`가 활동·휴회·비활동·졸업인 행에 `auth_user_id`로 연결된 계정"을 기준으로 막는다. 그런데 가입 트리거가 이 기준을 관리자 승인 없이 통과시키는 경로가 있어 STEP 20·21만으로는 의미가 없다. 이 문서는 그 경로를 닫는 설계(STEP 22)와 학회 코드를 서버에서 확인하는 방안(STEP 23)을 정리한다. 실행 방법은 `supabase/COPY_PASTE_ORDER.md`의 22·23절에 있다.

## 1. 지금 흐름 (코드 기준)

```text
app/signup/page.js (브라우저)
  1. 학회 코드를 번들 안의 고정 문자열과 비교          ← 번들·git 기록에 공개, signUp 직접 호출이면 건너뜀
  2. supabase.auth.signUp (공개 키)                    → auth.users 행 (이메일 인증 전)
  3. profiles insert (id, name, student_id) (공개 키)
        │
        ▼ 트리거 profiles_sync_member → public.sync_profile_to_member() (security definer, STEP 8)
  4. 이 계정에 이미 연결된 members 행이 있으면 그 행 갱신
  5. 없으면 이름(normalize_member_name)·기수 숫자가 같고 auth_user_id·legacy_profile_id가
     비어 있는 members 행이 정확히 1개인지 찾음
       ├─ 1개 → 그 행에 auth_user_id 연결 (상태는 그대로: active·alumni면 즉시 승인 학회원)   ← 구멍
       └─ 0개·2개 이상 → 새 members 행 (status pending, is_public false)
  6. profiles.member_id = 그 행

app/admin/hub/members/page.js (관리자)
  - 가입 승인 대기 탭 = status pending 행. 체크 후 "활동으로 이동"/"졸업으로 이관"
    → admin_bulk_set_member_status (STEP 8, is_admin 확인)
  - 계정을 기존 학회원 행에 붙이는 기능은 없다. 기존 명단 학회원이 계정을 얻는 길은 5번 자동 연결뿐이다.

app/components/MemberShell.js
  - members.auth_user_id = 로그인 계정 행을 읽어 이름 표시. 승인 여부로 막지 않는다
    (승인 대기 안내 패널은 별도 작업 relaxed-grothendieck-3a798f).
```

공격 경로: 공개 `/members`에 이름·기수가 나오고 학회 코드는 번들에 있다. 아직 계정이 없는 활동·졸업 학회원의 이름·기수로 가입하면 5번에서 그 행을 차지해 바로 승인 학회원이 되고, STEP 20·21을 통과해 그 사람의 출결·벌금·사유서·점수를 본다. STEP 21 결과의 `signup_auto_link` 행이 이 대상 수(계정 없는 승인 학회원 수)와 지금까지 자동 연결된 계정 수를 보여 준다.

## 2. 바뀐 흐름 (STEP 22)

```text
가입 (공개 키)
  signUp → auth.users                                   (STEP 23: 여기서 학회 코드 확인)
  profiles insert
     │ sync_profile_to_member() (새 정의)
     ├─ 이 계정에 이미 연결된 행이 있음 → 그 행만 갱신 (승인된 행의 이름·기수·계정은 바꾸지 않음)
     ├─ 로그인 계정이 없는 가입 정보 → 거절 (공개 키로 대기열 채우기 방지)
     └─ 그 밖 → 항상 새 승인 대기 행 (이름·기수가 같은 기존 학회원이 있어도 연결 안 함)

관리자 학회원 화면 → 가입 승인 대기 탭
  각 신청 아래 줄: 로그인 이메일 · 이메일 인증 여부 · 가입일 · 신청 행에 남은 기록 수
                   public.admin_signup_requests()  (관리자·열람자, security definer)
     ├─ [기존 학회원 이명단(30기 · 활동)에 연결]  이름·기수 같음 / 이름만 같음 후보
     ├─ [다른 기존 학회원에 연결…]                 계정 없는 기존 학회원 직접 선택 (이름 오타 대비)
     └─ 새 학회원이면 지금처럼 체크 → 활동으로 이동 / 졸업으로 이관
                                     (이름·기수 같은 후보가 있으면 확인창에 중복 경고)

연결 버튼 → public.admin_link_signup_to_member(신청 행, 기존 학회원)  (최고관리자·관리자·운영진)
  1. 확인: 신청 행은 pending이고 로그인 계정이 있음. 기존 학회원 행은 계정이 비어 있고,
     로그인 계정이 살아 있는 다른 가입 정보가 붙어 있지 않음
  2. 같은 학기 명단·세션 참여에 둘 다 있으면 기존 학회원 쪽을 남기고 신청 쪽 행은 기록 후 지움
  3. members.id를 가리키는 모든 외래 키 열(profiles·출결·벌금·사유서·제출물·댓글·발표·점수·학기 명단…)을
     신청 행 → 기존 학회원 행으로 옮김
  4. 계정이 이미 삭제된 예전 가입 정보가 기존 학회원을 가리키면 연결만 뗌 (행은 남김)
  5. 신청 행 삭제 → 기존 학회원 행에 auth_user_id·legacy_profile_id 연결
  6. ig_backup_step22.link_log에 신청 행 전체·연결 전 기존 학회원 행·옮긴 수·지운/뗀 행 전체를 남김
  → 그 계정은 즉시 is_approved_member() = true (기존 학회원이 승인 상태일 때). SQL 재실행 필요 없음.
```

### 왜 "연결 요청 열"이나 별도 큐 테이블을 만들지 않았나

- 승인 대기 행 자체가 이미 신청 큐다. 후보는 `admin_signup_requests()`가 볼 때마다 다시 계산하므로 명단이 바뀌어도 낡지 않고, 후보가 2명 이상이거나 이름만 같은 경우(지금은 조용히 중복 대기 행이 되던 경우)도 같은 화면에서 처리한다.
- 별도 큐에 두고 members 행을 만들지 않으면, 대기 중인 계정이 "학회원 행 없음"이 되어 MemberShell 안내·STEP 20 `blocked_accounts()` 분류가 갈리고, 관리자 화면에 대기 목록이 두 종류가 된다.
- `data_migration_issues`는 2026-08 이관의 미연결 기록 검토 큐(STEP 17)라 성격이 다르다.

## 3. 기록이 유지되고 중복 행이 남지 않는 근거

| 걱정 | 처리 | 확인 (PGlite, 아래 5절) |
| --- | --- | --- |
| 기존 학회원의 출결·벌금·사유서·제출물 | 기존 학회원 행(`members.id`)을 가리키므로 건드리지 않는다. 이름·기수·상태·공개 여부·`legacy_pr_member_id`도 그대로 | 연결 전후 값 동일, 출결 2건 유지 |
| 승인 대기 중에 쓴 기록 (STEP 17 자동 채움으로 신청 행 ID가 들어간 기록) | `members.id`를 가리키는 모든 외래 키 열을 찾아 기존 학회원으로 옮긴다 (테이블을 하드코딩하지 않음) | 출결 1건·사유서 1건 이동, 합계 3건 |
| 신청 행이 남아 명단이 두 줄 | 참조를 모두 옮긴 뒤 신청 행을 지운다. 지운 행 전체는 `link_log.request_row`에 남는다 | 신청 행 없음, `link_log`에 전체 |
| 같은 학기 명단에 둘 다 있음 (`unique(semester_id, member_id)`) | 기존 학회원 쪽을 남기고 신청 쪽 행은 `link_log.removed`에 남긴 뒤 지운다. 겹치지 않는 학기는 옮긴다 | 학기당 1행 |
| 그 밖의 유일 제약 충돌 | 전체를 되돌리고 "두 학회원 행이 같은 항목을 함께 가지고 있어 합칠 수 없습니다" 오류 | — |
| 외래 키 없이 학회원 ID를 적은 열 | 옮기지 않는다 (외래 키 기준) | 대시보드식 테이블 그대로 |
| 두 관리자가 동시에 누름 | 두 행을 `for update`로 잠근다. 두 번째는 "가입 신청을 찾을 수 없습니다" | 재클릭 거절 |
| 이미 계정이 있는 학회원에 또 연결 (계정 바꿔치기) | 거절. 계정 교체는 이 기능의 범위가 아님 | 거절 |
| 이메일 인증 전 계정 | 막지 않고 화면에 "이메일 인증 전" 표시 (프로젝트의 이메일 인증 설정과 무관하게 동작) | — |
| 승인 학회원이 가입 정보(profiles)를 고침 | 예전에는 트리거가 명단 이름·기수를 덮어썼다. 이제 승인된 행은 비어 있는 계정 연결만 채운다 | 이름·기수 그대로 |

STEP 22 SQL 자체는 공개 테이블 행을 추가·수정·삭제하지 않는다. 행이 바뀌는 것은 관리자가 연결 버튼을 누를 때뿐이다. 실행 중 확인은 가상 학회원·계정·가입을 하위 트랜잭션에서 만들고 항상 되돌린다.

## 4. 기존 학회원이 계정을 얻는 경로가 끊기지 않는 근거

| 경우 | 지금 (STEP 8) | STEP 22 후 |
| --- | --- | --- |
| 명단에 있고 이름·기수를 똑같이 입력 | 가입 즉시 자동 연결 (본인 확인 없음) | 승인 대기 → 관리자가 이메일 확인 후 [연결] 한 번 → 즉시 승인 학회원, 예전 기록 그대로 |
| 이름 띄어쓰기·기수 표기 차이 ("30기"/"30") | 자동 연결 (숫자만 비교) | 같은 후보로 "이름·기수 같음" |
| 기수를 비우거나 틀림 | 중복 승인 대기 행 → 관리자가 승인하면 명단 두 줄, 예전 기록과 끊김 | "이름만 같음" 후보로 연결 가능 |
| 이름 오타·별명 | 중복 승인 대기 행 | [다른 기존 학회원에 연결…]에서 직접 선택 |
| 같은 이름·기수 학회원이 2명 | 중복 승인 대기 행 | 두 후보가 모두 나오고 관리자가 고름 |
| 예전 계정이 삭제되고 가입 정보만 남은 학회원 | 자동 연결 안 됨 (legacy_profile_id가 차 있어서) → 중복 | 연결 가능 (예전 가입 정보는 연결만 떼고 기록) |
| 2026-08 이관 때 이미 생긴 중복 승인 대기 행 | 합칠 방법 없음 | 같은 버튼으로 합침 (신청 행 기록도 옮김) |
| 새 학회원 | 승인 대기 → 활동으로 이동 | 그대로 |

즉 지금 자동 연결되던 모든 경우가 "관리자 버튼 한 번"으로 바뀌고, 지금 중복으로 끝나던 경우는 새로 해결된다. 끊기는 경우는 없다. 대가는 기존 학회원 가입마다 관리자 확인이 한 번 필요하다는 것이며, 이는 STEP 20·21이 전제하는 승인 모델과 같다. 연결 함수가 실패하면 기존 학회원이 계정을 못 얻으므로, STEP 22는 실행 중 가상 연결이 실패하면 전체를 되돌린다.

## 5. 검증 (PGlite 0.2.17, 스크래치패드, 저장소에 넣지 않음) — 97/97 통과

비슈퍼유저 소유자 역할(SQL Editor처럼), `anon`·`authenticated`·`supabase_auth_admin`, Supabase식 `auth.uid()`, `auth.users`는 Auth 역할 소유(SQL Editor 역할은 읽기·쓰기·트리거 권한만), 대시보드식 `profiles`(공개 키 insert 허용, 본인 읽기·수정), STEP 8 트리거 원문, STEP 9 원문, STEP 20 `is_approved_member()`.

- STEP 22 전: 명단 이름·기수로 가입하면 승인 학회원 행을 차지하고 즉시 승인됨 (구멍 재현). 계정 없는 가입 정보는 STEP 8에서도 `requested_status` NOT NULL 오류로 이미 실패함.
- STEP 22 실행: 결과 9행 모두 정상, 가상 확인 5개 실제 실행(`skipped` 없음), 남는 행 없음. 재실행 시 첫 스냅샷 유지.
- 이후 가입: 기존 행 차지 안 함, 본인 승인 대기 행, 승인 전 상태. 계정 없는 가입 정보 거절.
- 목록: 공개 키·일반 계정 호출 불가, 열람자 가능. 이메일, 이름·기수 같음/이름만 같음 후보, 계정이 살아 있는 다른 가입 정보가 붙은 학회원은 "연결 불가" 표시.
- 연결: 본인·열람자·공개 키 불가. 계정 있는 학회원·다른 계정의 가입 정보가 붙은 학회원·자기 자신·승인 대기가 아닌 행 거절. 성공 시 위 3절 표의 모든 항목, 연결 직후 `is_approved_member()` true, 재클릭·두 번째 신청 거절. 계정이 삭제된 예전 가입 정보는 떼고 기록, 남은 `legacy_profile_id`만 있는 경우 교체.
- 새 학회원 승인 그대로. 되돌리기: 관리자 함수 삭제, 예전 자동 연결 복귀, `link_log` 유지, 재적용 정상.
- 안전장치: 가상 가입이 실패하는 환경(profiles 트리거 고장)에서 `probe failed at signup`으로 전체 취소.
- STEP 23: 코드 없음·틀린 코드·예전 공개 코드 거절, 맞는 코드(앞뒤 공백 허용) 통과·메타데이터에서 제거, 메타데이터 수정 때도 제거, 초대 계정 통과, 코드 해시 저장, 로그인 계정이 `ig_private` 읽기·코드 변경·트리거 함수 직접 호출 불가, 트리거 함수 실행 권한 없이도 Auth 역할 insert에서 동작. 재실행 시 코드 유지. 되돌리기(함수 CASCADE) 후 코드 없이 가입 가능, 재적용 정상. STEP 23 설치 후에도 STEP 22 가상 확인(초대 경로) 정상.

PGlite는 GoTrue(Supabase Auth 서버)를 흉내 내지 않는다. 실제 가입 화면에서 STEP 23 거절이 "Database error saving new user"로 오는지, Supabase가 SQL Editor 역할에 `auth.users` 행 insert(확인용)·트리거 생성을 허용하는지는 운영에서 처음 실행할 때 결과 표로 확인한다. 허용하지 않으면 확인 행이 `skipped`로 나오고 정의 기준으로만 판단한다.

## 6. 학회 코드 서버 확인 (STEP 23) 검토

지금 코드는 번들(`app/signup/page.js`)과 git 기록에 공개돼 있고, `supabase.auth.signUp`을 공개 키로 직접 부르면 코드 확인 자체를 건너뛴다. 그래서 **어느 방안이든 새 코드로 바꿔야 한다**. 새 코드는 저장소·채팅·`NEXT_PUBLIC_*` 환경 변수에 두지 않는다(모두 공개된다).

| 방안 | 동작 | Supabase 허용 | 장점 | 단점 |
| --- | --- | --- | --- | --- |
| A. `auth.users` BEFORE INSERT 트리거 (채택) | 가입 메타데이터 `signup_code`를 비공개 스키마의 해시와 비교, 틀리면 insert 중단, 맞으면 메타데이터에서 지움 | 2025-04-21 auth 스키마 제한 후에도 `auth.users`에 트리거 생성은 허용. auth 스키마에 새 함수는 못 만들므로 함수는 `public`에 security definer로 둔다 | SQL Editor만으로 끝남, 요금제 무관, 확인과 삭제가 한 곳 | 거절 문구가 "Database error saving new user"(HTTP 500)로 뭉뚱그려짐. 트리거를 지우거나 바꿀 때 테이블 소유권이 필요할 수 있어 되돌리기는 함수 CASCADE로 한다 |

A를 채택하고, 거절 문구를 바꾸고 싶으면 나중에 B를 확인용으로만 추가할 수 있다. 초대(`invited_at`이 있는 계정: 대시보드 Invite user)는 코드 없이 만들어진다. 대시보드 "Add user"로 바로 만드는 계정은 거절되므로 초대를 쓴다. 다른 인증 제공자(구글 로그인 등)를 켜면 그 가입도 코드가 없어 거절된다.

순서: 가입 화면이 `signup_code`를 보내도록 배포한 **직후** STEP 23을 실행하고, 바로 `select ig_private.set_signup_code('학회 코드');`를 실행한다(학회 결정으로 지금 코드를 그대로 쓴다). 배포 전에 실행하면 예전 화면이 코드를 보내지 않아 가입이 모두 거절되고, 배포 후 STEP 23 전까지는 코드 확인이 아예 없다(지금도 사실상 없음). 모집 기간을 피해 한 번에 한다.

## 7. 남는 위험과 후속

- **이미 자동 연결된 계정**: STEP 22는 풀지 않는다(정상 학회원을 잠글 수 있음). 결과의 `already_auto_linked`와 `select * from ig_backup_step22.auto_linked_accounts();`(이메일 포함)로 본인 여부를 확인한다. 2026-08 이관 때 연결된 예전 계정도 섞여 나올 수 있다. 남의 계정이면 지금은 관리자 화면에서 풀 방법이 없으므로(계정 연결 해제 기능 없음) 그 계정을 알려 주면 따로 처리 SQL을 만든다.
- **`pr_members` 쓰기**: 로그인 계정이 `pr_members`에 쓰면 `sync_pr_member_to_member`(security definer)가 같은 이름·기수 학회원 행 상태를 활동으로 바꾼다. STEP 21이 쓰기를 관리자 전용으로 막는다. STEP 22 결과 `other_paths`가 STEP 21 미실행을 알려 준다.
- **이메일만으로 본인 확인**: 관리자가 이메일을 보고 판단한다. 같은 이름의 다른 사람이 가입하면 이메일로 구별해야 하므로, 연결 전 학회 단톡방 등으로 한 번 확인하는 운영 규칙이 필요하다.
- **MemberShell 승인 대기 안내**(별도 작업): 안내 문구에 "이미 명단에 있는 학회원은 운영진이 기존 기록과 연결합니다"를 넣으면 기존 학회원이 혼란스럽지 않다.
- **계정 교체**(이메일을 잃어 새 계정으로 가입한 학회원): 이 기능은 계정이 빈 학회원에만 연결한다. 필요하면 별도 기능으로 다룬다.
